Use a typed Python client when an application knows the service contract, or the CLI shell when an operator needs to inspect a peer. Raw transport is an integration surface for tools that already manage the protocol and codecs.

First run the [Python first service](/docs/quickstart/python/) and keep its producer running. The snippets use that shared service module and a real producer address in place of `aster1...`. For other languages, follow the corresponding [client reference](/docs/bindings/); the admission sequence below describes the Python high-level client.

| Approach | When to use | Needs local types? |
|----------|------------|-------------------|
| **Typed client** | Application code, CI pipelines, production services | Yes |
| **Aster shell** | Exploration, debugging, ad-hoc calls, ops | No |
| **Raw transport** | Custom tooling and protocol testing | Payload schema and codec required |

## 1. Typed client (recommended for application code)

The typed client gives you IDE autocomplete and type checking where supported by your language tooling. You need the service's Python type definitions (the `@service`-decorated class and its request/response dataclasses).

```python
import asyncio
from aster import AsterClient
from hello_service import HelloService, HelloRequest

async def main():
    async with AsterClient() as c:
        hello = await c.client(HelloService)
        resp = await hello.say_hello(HelloRequest(name="World"))
        print(resp.message)  # Hello, World!

asyncio.run(main())
```

Save the block as `consumer.py` in the first-service project. Set `ASTER_ENDPOINT_ADDR` to the current producer ticket before running it.

The consumer needs:
- **The producer's endpoint address** -- printed on startup, or set via `ASTER_ENDPOINT_ADDR`
- **The service type definitions** -- the same `@service` class (or a compatible package) as the producer

### How it works

1. `AsterClient` connects to the producer's admission endpoint
2. The admission response lists available services (name, version, contract_id)
3. `client.client(HelloService)` matches the local class to the remote service by name + version
4. A QUIC connection opens on `aster/1` and a typed `ServiceClient` is returned
5. Method calls serialize via Fory XLANG → send frame → receive frame → deserialize

### Getting the types

Service authors can publish a client package containing the type definitions. The following package name is illustrative; use your service team's actual package:

```bash
pip install billing-service-types  # published by the service team
```

```python
from billing_types import BillingService, InvoiceRequest
```

For internal services, the types often live in a shared module imported by both producer and consumer.

### Identity and credentials

For dev mode (open gate), just set the address:

```bash
ASTER_ENDPOINT_ADDR="<addr>" python consumer.py
```

For production, use an `.aster-identity` file:

```bash
# Generate with the CLI:
aster enroll node --profile prod --role consumer --name my-consumer

# Then just run -- the identity file provides everything:
ASTER_ENDPOINT_ADDR="<addr>" python consumer.py
```

See [AsterClient](/docs/bindings/python/client) for the full Python API reference.

## 2. Aster shell (for exploration and debugging)

The Aster shell connects to any peer and lets you browse services, inspect contracts, and invoke methods interactively -- without needing the Python type definitions locally.

```bash
# Connect to a producer
aster shell <endpoint-addr>

# Or explore in demo mode (no live peer needed)
aster shell --demo
```

### What the shell can do

```
producer:/$ ls
  blobs/     services/     gossip/

producer:/$ cd services
producer:/services$ ls
  Service         Methods    Version    Pattern
  HelloService          1         v1    shared

producer:/services$ cd HelloService
producer:/services/HelloService$ ls
  Method       Pattern    Signature
  say_hello    unary      (HelloRequest) -> HelloResponse

producer:/services/HelloService$ ./say_hello name="World"
-> HelloService.say_hello(name='World')
(42ms)
{
  "message": "Hello, World!"
}
```

### Dynamic invocation without local types

The shell invokes methods without local type definitions. When connected to a peer, the shell reads contract
manifests and synthesizes wire-compatible types at runtime. Field names, types,
defaults, and Fory wire tags are all extracted from the manifest, so the shell
can build correctly serialized requests on the fly. This means you can inspect
and invoke compatible services from the shell without installing the service's client
package.

### How it discovers methods

The shell reads the service contract from the producer's registry:

1. Admission response includes a **registry ticket** (read-only iroh-docs share)
2. The shell joins the registry doc and reads `ArtifactRef` entries
3. Each ArtifactRef points to a blob collection containing `manifest.json`
4. The manifest has full method schemas: names, patterns, field definitions with types and defaults
5. Tab completion and interactive prompting work from this metadata

### Shell features

- **Filesystem-like navigation** -- `cd`, `ls`, `pwd`, `cat`, `save`
- **Tab completion** -- service names, method names, argument names
- **Interactive prompting** -- call a method with no args and it prompts for each field
- **All streaming patterns** -- server-stream displays values as they arrive, bidi shows split input/output
- **Contract introspection** -- `describe` shows the full contract tree
- **Rich output** -- tables, syntax-highlighted JSON, progress bars
- **Session subshell** -- `session Analytics` opens a dedicated session for session-scoped services

### Scripted calls

Use `aster call` for a non-interactive method invocation. The [CLI reference](/docs/reference/cli/) gives the command syntax and installation limits. Shell navigation and protocol-specific commands do not all have equivalent top-level subcommands.

## 3. Raw transport (for custom tooling)

For advanced use cases -- custom tooling, testing, or building clients in languages without a typed binding -- you can use the transport layer directly:

```python
from aster import IrohTransport, ForyCodec, SerializationMode
from hello_service import HelloRequest, HelloResponse

# Use an existing admitted Iroh connection; register both payload types.
codec = ForyCodec(
    mode=SerializationMode.XLANG, types=[HelloRequest, HelloResponse],
)
transport = IrohTransport(connection, codec=codec)

# Invoke by service and method name
result = await transport.unary(
    service="HelloService",
    method="say_hello",
    request=HelloRequest(name="World"),
)
```

This is an API fragment: an admitted `connection` to the matching server must already exist. This Python transport accepts a request object and encodes it with the configured codec; the lower-level native RPC API accepts bytes. Close the transport and its owning node when finished. The raw transport still requires serializable request/response types. For invocation without local type definitions, use the shell or fetch the manifest and construct compatible payload types from its field definitions.

## Python high-level admission flow

Python `AsterClient` runs consumer admission before returning its high-level service client. Native Rust, Go, and .NET direct RPC connections do not universally run this Python discovery handshake; applications must configure the admission and attribute-verification path their server requires.

<MermaidDiagram source={"sequenceDiagram\n    participant C as Consumer\n    participant P as Producer\n    C->>P: QUIC connect (aster.consumer_admission)\n    C->>P: credential (or empty for dev mode)\n    P->>P: verify / auto-admit\n    P-->>C: services list + registry ticket\n    C->>P: QUIC connect (aster/1)\n    C->>P: RPC calls\n"} />

The admission response gives the consumer:
- **services** -- list of available services with name, version, contract_id
- **registry_ticket** -- read-only doc ticket for full contract metadata
- **root_pubkey** -- for independent credential verification

Even in dev mode (open gate), the admission handshake runs to discover services.

## Error handling

Python callers can encounter the errors below. CLI tools report failures through their own output and exit behavior; other bindings use their own error types.

| Error | Meaning |
|-------|---------|
| `PermissionError` | Admission denied (invalid credential, wrong root key) |
| `LookupError` | Service not offered by this producer |
| `RpcError` | Call failed (check `e.code`: NOT_FOUND, DEADLINE_EXCEEDED, INTERNAL, etc.) |
| `ConnectionError` | QUIC connection lost |

```python
from aster import RpcError, StatusCode

try:
    resp = await hello.say_hello(HelloRequest(name=""))
except RpcError as e:
    if e.code == StatusCode.DEADLINE_EXCEEDED:
        print("Call timed out")
    elif e.code == StatusCode.PERMISSION_DENIED:
        print("Not authorized for this method")
```

## Verify a call and a denial

A successful first-service call prints `Hello, World!`. If connection succeeds but the service lookup fails, compare its name, version, and contract metadata with the producer. If a method returns `PERMISSION_DENIED`, inspect the verified caller attributes and that method's requirement. A transport connection and a service listing do not prove method authorization.

Before using protected credentials in an application, repeat the call with an intentionally unauthorized principal and confirm rejection at the server. A timeout leaves a mutating operation's outcome uncertain; reconcile application state before retrying it.
