Aster is a multi-language SDK built around a shared Rust engine. The Rust facade and language bindings expose typed services, while Rust implements the transport, RPC dispatch, wire envelopes, and shared security checks.

## SDK layers

<MermaidDiagram source={"graph TD\n    API[\"Rust facade and Python / TypeScript / Go / Java / .NET APIs\"] --> RPC[\"Shared Rust RPC dispatch and transport adapters\"]\n    RPC --> CORE[\"aster_transport_core: endpoints, wire codecs, trust, data protocols\"]\n    CORE --> IROH[\"Iroh: QUIC, blobs, documents, gossip\"]\n    IROH --> NET[\"Direct network paths and encrypted relay traffic\"]\n"} />

- **Rust facade (`aster`)** provides the Rust RPC API, dispatch, transport adapters, and native-stack access.
- **Language APIs** adapt service definitions, handler calls, and payload types to Python, TypeScript, Go, Java, and .NET.
- **Native bridges** use PyO3, NAPI-RS, or the C ABI to connect language runtimes to the Rust engine.
- **Transport core** manages endpoints, protocol routing, framing, canonical contracts, and Iroh data operations.
- **Iroh** provides authenticated QUIC connectivity, relay support, blobs, document replication, and gossip.

For example, the Python server uses Rust dynamic dispatch for header decoding, method lookup, serialization checks, session rules, capabilities, and deadlines. Python runs the application handlers and its interceptor chain.

## One endpoint, multiple protocols

<MermaidDiagram source={"graph TD\n    NODE[\"IrohNode\"]\n    ROUTER[\"Router\"]\n\n    NODE --> ROUTER\n\n    ROUTER --> BLOBS[\"iroh-blobs<br/><code>BLOBS_ALPN</code>\"]\n    ROUTER --> DOCS[\"iroh-docs<br/><code>DOCS_ALPN</code>\"]\n    ROUTER --> GOSSIP[\"iroh-gossip<br/><code>GOSSIP_ALPN</code>\"]\n    ROUTER --> RPC[\"Aster RPC<br/><code>aster/1</code>\"]\n    ROUTER --> CA[\"Consumer Admission<br/><code>aster.consumer_admission</code>\"]\n    ROUTER --> PA[\"Producer Admission<br/><code>aster.producer_admission</code>\"]\n\n    RPC --> QH1[\"AsterQueueHandler\"]\n    CA --> QH2[\"AsterQueueHandler\"]\n    PA --> QH3[\"AsterQueueHandler\"]\n"} />

The Iroh router selects a protocol handler using the connection's ALPN. RPC, admission, blobs, documents, and gossip can share an endpoint identity and network configuration. Different ALPNs use separate QUIC connections; an RPC connection does not carry blob or gossip streams.

The core's `AsterQueueHandler` routes custom-protocol connections into a bounded channel. The shared Rust RPC runtime accepts and dispatches RPC traffic. Applications can also register custom protocols through the native APIs.

## Async execution

Rust executes asynchronous network operations on Tokio. Python's PyO3 bridge exposes awaitables, and the TypeScript NAPI-RS bridge exposes promises. The C ABI exposes handles and completion events for other bindings. Application handlers follow their binding's concurrency model.

## Contracts and payloads

The framework derives a canonical descriptor from a service definition and hashes it with BLAKE3. The resulting `contract_id` identifies that descriptor across bindings. Method names, wire types, and canonical settings must agree; the ID does not verify application behavior.

See [contract identity](/docs/concepts/contract-identity/) for canonical encoding and [serialization](/docs/concepts/serialization/) for payload settings.

## RPC framing

<MermaidDiagram source={"sequenceDiagram\n    participant C as Client\n    participant S as Server\n\n    C->>S: Open QUIC bidirectional stream\n    C->>S: Frame: StreamHeader (HEADER flag)<br/>service, method, version, metadata\n    C->>S: Frame: Request payload (Fory-serialized)\n    S->>C: Frame: Response payload (Fory-serialized)\n    S->>C: Frame: RpcStatus trailer (TRAILER flag)<br/>code: OK\n"} />

Headers and status trailers use AEv1, a binary encoding independent of Fory. Request and response payloads use Fory XLANG for cross-language calls. Frames carry a length and flags, including `HEADER` (`0x04`), `TRAILER` (`0x02`), and `COMPRESSED` (`0x01`). Payloads strictly larger than 4096 bytes are compressed by default.

Session-scoped services use connection-scoped session IDs across call streams. They do not require one persistent stream per service instance. See [session-scoped services](/docs/concepts/session-scoped-services/).

## Deployment identity

A node's secret key determines its endpoint identity. Enrollment credentials and method capability requirements provide deployment authorization under the configured root key. Operator profiles and identity files are configuration mechanisms; they must be protected according to the keys and credentials they contain.

Development settings are permissive. Read the [trust model](/docs/concepts/trust-model/) and [configuration reference](/docs/reference/configuration/) before deploying access-controlled services.
