Your first call establishes that two peers can connect, agree on a request and
response, and execute a service method. The next step depends on what your
application needs to do. Keep the working example as a checkpoint: add one
capability and verify its result before changing the next part.

## Extend your service

| What your application needs | Next step | What to verify |
| --- | --- | --- |
| Return progress or results over time | Add a server-streaming method using your language's server guide. | The client sees messages incrementally and can stop receiving. |
| Upload many records in one call | Add a client-streaming method. | The server reads incrementally and reports its final result. |
| Exchange ongoing commands and results | Add a bidirectional method. | Sending and receiving can proceed concurrently; each side handles cancellation. |
| Keep client-specific state across calls | Use [session-scoped services](/docs/concepts/session-scoped-services/). | Two sessions have separate state, even on one connection. |
| Connect another language | Follow the [cross-language example](/docs/examples/cross-language/). | Request fields and response values survive the language boundary. |

Continue with the server and client references for your language:
[Rust](/docs/bindings/rust/), [Python](/docs/bindings/python/),
[TypeScript](/docs/bindings/typescript/), [Go](/docs/bindings/go/),
[Java and Kotlin](/docs/bindings/java/), or [.NET](/docs/bindings/dotnet/).
The APIs differ, including how streaming handlers are registered and who owns
session resources.

## Inspect calls interactively

The Aster shell lets you inspect published services and invoke methods without
writing another client. Install the CLI separately using the
[CLI reference](/docs/reference/cli/), keep the producer running, and pass its
current address:

```bash
aster shell <endpoint-addr>
```

Browse the service names the producer actually advertises. The Rust quickstart
hosts `Echo`; the Python and TypeScript quickstart hosts `HelloService`.
The [dialing guide](/docs/guides/dial-a-service/) explains the shell workflow
and credential requirements. Successful SDK calls do not by themselves
qualify every shell command against every binding.

## Connect an AI tool client

An MCP bridge translates a service's published contract into tools an
MCP-compatible client can invoke. This is useful when an assistant needs to
query application state or request an action through your existing service.

Start with [MCP integration](/docs/guides/mcp-integration/). Choose which methods
to expose and configure the bridge's credentials. A tool description exposes
a callable interface; the server still needs to authorize the action.

## Add shared data

A method call is transient. If callers need content after the call finishes,
choose a storage or replication mechanism:

- [Blobs and documents](/docs/guides/data/) store content and replicate entries
  that refer to it.
- [Sealed grants](/docs/guides/sealed-grants/) distribute data capabilities to
  intended recipients.
- [Coordination](/docs/guides/coordination/) orders decisions that competing
  writers must agree on.
- [Fenced leases](/docs/guides/leases/) protect a resource from writes made by
  an owner whose lease has ended.

Begin with the data guide's choice table. Use [topology](/docs/guides/topology/)
when choosing where work should run; an observed placement preference does not
grant exclusive ownership.

## Prepare a deployment

The quickstarts use permissive admission and temporary identities. Before
using real data, follow the [trust model](/docs/concepts/trust-model/) and your
language's server guide to choose an access policy. Test both an allowed call
and a denied call.

Then use [operating a node](/docs/guides/operations/) to preserve identity and
state, check readiness, observe failures, and shut down. A first successful
call is the starting point for testing restart, recovery, and access boundaries.
