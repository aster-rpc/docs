Aster separates peer identity from application permission. [Iroh](https://iroh.computer/)
authenticates the endpoint key on a QUIC connection. Your admission policy decides
whether that peer may connect, and method requirements decide which operations
an admitted caller may invoke.

These protections depend on configuration. A service started with permissive
admission is reachable without deployment enrollment. Rust and the higher-level
bindings do not provide identical enrollment workflows.

## Authorization stages

| Stage | Decision | Implementation boundary |
| --- | --- | --- |
| Gate 0: connection admission | May this peer connect on this protocol? | Endpoint hooks and the application's admission policy |
| Gate 1: credential admission | Does this credential establish deployment membership? | High-level enrollment workflow or application verification |
| Gate 2: service policy | May this caller start or use this service/session? | Service authorization and application interceptors |
| Gate 3: method capabilities | Do the caller's verified attributes satisfy this method? | Shared Rust dispatcher checks declared requirements |

These are separate checks. Authenticating a key does not grant a role, and
opening a session does not remove a method's capability requirement.

## Trace an allowed and a denied call

Suppose a worker may report status and an operator may cancel jobs. The
application independently configures the deployment root, verifies enrollment
material, and attaches verified attributes to the authenticated caller.
`cancel_job` requires the operator role.

| Request | Decision | Result |
| --- | --- | --- |
| Enrolled operator with verified `aster.role=operator` calls `cancel_job` | Admission and method requirement succeed | Dispatcher invokes the handler |
| Enrolled worker with verified `aster.role=worker` calls `cancel_job` | Method requirement fails | Dispatcher rejects the call before the handler |
| Caller supplies `aster.role=operator` in unverified metadata | Metadata establishes no authority | Policy must not promote it into verified attributes |
| Peer presents a credential signed by an untrusted root | Enrollment verification fails | Protected admission rejects it |

A denied-call test should also confirm that the handler did not mutate state.
Use separate test peers and repeat the test over each enabled transport.

## Select the policy integration

| Surface | Application responsibility | Reference |
| --- | --- | --- |
| Python high-level server/client | Configure a trusted root and consumer credentials; disable permissive admission | [Python server](/docs/bindings/python/server/) |
| TypeScript high-level server/client | Provision identity and consumer credentials; keep protected admission enabled | [TypeScript server](/docs/bindings/typescript/server/) |
| JVM high-level server/client | Configure root and credentials; choose consumer admission or an explicitly supported direct-RPC path | [JVM server](/docs/bindings/java/server/) |
| Rust | Run connection hooks and supply verified peer attributes explicitly | [Rust server](/docs/bindings/rust/server/) |
| Go, .NET | Wire the binding's gate and verified policy context; follow its ownership rules | [Language guides](/docs/bindings/) |
| HTTP / WebTransport | Authenticate a principal independently of Iroh endpoint identity | [HTTP serving](/docs/guides/http/) |

The references describe API integration. A complete protected deployment also
needs independent root provisioning, credential expiry/replay policy, health
checks, and negative tests; see [operations](/docs/guides/operations/).

## Configure Rust admission explicitly

Rust exposes connection admission and the shared method capability checks.
The high-level Python enrollment and session-authorization workflows are not
automatically installed by the Rust server builder. Rust applications must wire
their own verified admission/attribute policy.

Enable hooks in configuration and keep the admission loop running. The default
hook failure mode is fail-open: a missing answer or stalled loop can lead to
acceptance after the timeout. Use `HookFailureMode::FailClosed` when failure to
verify must reject a peer. Account for outbound hooks as well as inbound ones.

Use the independent deployment root when verifying ownership or enrollment
material. Do not trust a root merely because it arrived inside the credential
being checked. Bind the verified identity to the connection's actual peer.

## Apply method requirements

The shared dispatcher checks declared capability requirements before invoking
the handler. The caller's attributes come from the verified policy context.
In Rust, `AttributeStore` holds peer attributes for authenticated Iroh calls;
only populate it from trusted application logic.

| Requirement | Meaning |
| --- | --- |
| `ROLE` | Match the caller's `aster.role` value |
| `ANY_OF` | Require at least one listed capability |
| `ALL_OF` | Require every listed capability |

A method with no requirement does not become restricted simply because another
method on the service has one. Review every public operation and the baseline
services. Descriptive roles in [NodeInfo](/docs/guides/baseline-services/) do not
populate caller authorization attributes.

## Enrollment and keys

High-level enrollment credentials can bind a producer endpoint to a root-signed
identity and attributes. Consumer workflows have their own credential and policy
forms. Use the workflow supported by your installed binding, verify expiry and
identity constraints, and enforce the intended replay policy for one-time tokens.

Keep the private deployment root offline except for authorized signing or recovery.
Nodes need the configured public root, their own endpoint secret, and the
credentials required by their role. Aster does not keep an operator's root
private key offline on their behalf.

An endpoint ticket supplies addressing information and may carry credential
material depending on its type. Review what you publish. Preserve a node's
secret key when its identity must survive restart.

## Authenticate HTTP separately

HTTPS and WebTransport do not carry an authenticated Iroh endpoint identity.
An application authenticator must verify HTTP or call credentials and return
an authorized principal and attributes. An incoming peer string or metadata
field is not proof of identity. Method capability checks still apply after
authentication. See [HTTP serving](/docs/guides/http/).

In-process calls have a different boundary again: there is no remote QUIC
handshake to evaluate. Do not use an in-process success as evidence that
network admission works. Application interceptors must handle their local-call
context explicitly.

## Revoke the authority that protects the resource

There is no universal revocation operation covering every protocol and every
secret already disclosed. Apply revocation at the relevant enforcement point:

- Remove or deny admission and authorization in the policy enforcing access.
- Advance the fence at a lease serializer to reject stale protected writes.
- Publish an explicit revoked grant record for cooperating recipients.
- Rotate a leaked namespace secret and re-grant it to remaining members.

Changing a gossip topic or discovery record does not by itself revoke an
existing connection, an independently known address, or a previously learned
capability. See [sealed grants](/docs/guides/sealed-grants/) and
[fenced leases](/docs/guides/leases/).

## Check the deployed policy

Test denied connections, missing and expired credentials, wrong roles, and
stalled policy callbacks. Repeat relevant tests over every enabled transport.
Use non-sensitive test data while checking permissive development examples.
