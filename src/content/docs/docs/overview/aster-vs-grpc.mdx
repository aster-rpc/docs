[gRPC](https://grpc.io/) and Aster offer typed RPC with unary and streaming calls. Their deployment models differ: gRPC commonly connects to named network services, while Aster connects to peers identified by public keys.

Aster is a public preview. Assess its compatibility and operational requirements before adopting it for production workloads.

## Comparison

| Dimension | gRPC | Aster |
| --- | --- | --- |
| Transport | Commonly HTTP/2 over TCP | Iroh QUIC with direct paths and relay fallback |
| Connection target | Usually hostname and port | Endpoint public key with network hints |
| Authentication | Configurable transport and call credentials | Endpoint-key authentication plus configured enrollment and method permissions |
| Serialization | Protocol Buffers by default; custom codecs available | Fory XLANG by default; additional modes depend on binding support |
| Service definition | Usually `.proto` and generated stubs | Language-native service definitions and canonical contract IDs |
| Network reachability | Supplied by the deployment network | Iroh attempts NAT traversal; relays can provide fallback |
| Discovery | Deployment-specific name resolution and registries | Explicit endpoint addresses or Aster's peer-replicated registry |
| Calls | Unary, server-streaming, client-streaming, bidirectional streaming | The same four patterns plus session-scoped services |
| Language surfaces | Established implementations and tooling across many languages | Preview surfaces for Rust, Python, TypeScript, Go, Java, and .NET |

## Connectivity

gRPC fits deployments that already provide routable services, name resolution, certificates, and HTTP-aware operational tooling. It does not require a service mesh or load balancer; those are deployment choices.

Aster uses [Iroh](https://iroh.computer/) to establish encrypted QUIC connections to endpoint identities. Iroh attempts direct paths and can forward encrypted traffic through relays. Aster therefore needs less application-managed addressing in some cross-network deployments, but it still depends on reachable network paths and any configured discovery or relay services.

QUIC streams avoid TCP's connection-wide delivery ordering across streams. They still share connection-level flow control, congestion control, and network capacity. Connection migration can preserve a connection across path changes when the new path is reachable. See [transport](/docs/concepts/transport/).

## Contracts and payloads

Protocol Buffers provides an explicit schema and a well-established code-generation workflow. Aster derives contracts from application code and uses a BLAKE3 `contract_id` to identify the canonical interface. Cross-language definitions must agree on wire names, types, and settings.

Aster uses [Apache Fory](https://fory.apache.org/) for XLANG payloads. Additional serialization modes have binding-specific limits. Dynamic tools can convert JSON input to XLANG. The legacy JSON RPC wire mode has been retired; opt-in browser JSON projections are available through the [HTTP transport](/docs/guides/http/). Encrypted packets remain encrypted regardless of serialization format. Measure representative payloads and end-to-end calls when comparing performance. See [serialization](/docs/concepts/serialization/).

## Sessions and permissions

Aster's session-scoped services retain an instance across typed method calls that carry the same connection-scoped session ID. This can simplify stateful interactions, though applications remain responsible for recovery after a session ends.

Aster also includes enrollment and method capability checks. These require an operator-defined trust policy; permissive development settings do not provide deployment authorization. See [session-scoped services](/docs/concepts/session-scoped-services/) and the [trust model](/docs/concepts/trust-model/).

## Choosing a framework

gRPC is a useful starting point when your team already relies on its schema tooling, HTTP integrations, or established language ecosystem. Aster is worth evaluating when endpoint identity, cross-network connectivity, or stateful peer sessions are central requirements and you can work within a public preview's stability limits.

Before choosing, check three practical conditions:

- Does your deployment already provide the routable services and HTTP tooling
  you need, or is reaching changing peers a central application problem?
- Can your chosen Aster binding express and run your actual payloads, streaming
  patterns, admission policy, and cleanup requirements?
- Can you operate persistent keys, any required relays, and application recovery
  while accepting preview API changes?
